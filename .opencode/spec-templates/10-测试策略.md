# 测试策略

## 测试金字塔

测试金字塔是指导测试分层的重要原则，强调底层测试（单元测试）数量要多于高层测试（集成测试、E2E测试）。这一结构反映了测试成本、执行速度和置信度之间的权衡。

```
                        ┌───────────────────┐
                        │                   │
                        │    E2E Tests      │     ▲
                        │  (端到端测试)      │     │
                        │                   │     │ 置信度
                        ├───────────────────┤     │ 递增
                        │                   │     │
                        │  Integration      │     │ 执行成本
                        │    Tests          │     │ 递增
                        │  (集成测试)        │     │
                        ├───────────────────┤     │
                        │                   │     │
                        │    Unit Tests     │     │
                        │  (单元测试)        │     ▼
                        │                   │
                        └───────────────────┘
```

### 各层测试比例

| 层级 | 占比 | 执行频率 | 维护成本 | 覆盖重点 |
|------|------|----------|----------|----------|
| 单元测试 | 70% | 每次提交 | 低 | 业务逻辑、边界条件 |
| 集成测试 | 20% | 每日构建 | 中 | API交互、数据流转 |
| E2E测试 | 10% | 每次发布 | 高 | 关键用户路径 |

### 分层原则

1. **底层测试优先**: 发现问题越早，修复成本越低
2. **测试独立性**: 每层测试应能独立运行，不依赖其他层的结果
3. **按需Mock**: 单元测试充分Mock外部依赖，集成测试适度使用真实组件
4. **快速反馈**: 单元测试应在秒级完成，集成测试分钟级，E2E测试可更长

## 单元测试

### 测试目标

单元测试针对代码的最小可测单元进行验证，通常是一个函数或一个类的方法。好的单元测试应具备以下特征：

- **快速**: 单个测试毫秒级完成
- **隔离**: 不依赖外部系统（数据库、网络、文件系统）
- **可重复**: 无论何时运行结果一致
- **自包含**: 自身提供测试数据，不依赖测试执行顺序
- **可维护**: 测试代码应与生产代码同等重视

### 覆盖率要求

| 模块类型 | 行覆盖率 | 分支覆盖率 | 函数覆盖率 |
|----------|----------|------------|------------|
| 核心业务逻辑 | ≥80% | ≥70% | 100% |
| 工具函数/工具类 | ≥90% | ≥80% | 100% |
| 数据模型/实体 | ≥70% | ≥60% | 100% |
| 边界/异常处理 | ≥85% | ≥75% | 100% |
| 遗留代码/重构区 | ≥60% | ≥50% | - |

### 单元测试要求

#### 必须测试的场景

1. **正常路径**: 给定有效输入，验证输出符合预期
2. **边界条件**: 空值、零值、最大值、极值、Unicode字符
3. **错误处理**: 异常捕获、错误码返回、资源清理
4. **分支覆盖**: if/else、switch、try/catch每个分支
5. **依赖Mock**: 所有外部依赖（数据库、API、文件系统）必须Mock

#### 不需要测试的内容

- 第三方库自带功能（应通过集成测试验证）
- 简单getter/setter（除非包含业务逻辑）
- 框架自动生成的代码

### 测试框架

| 语言 | 框架 | Mock库 | 断言库 |
|------|------|--------|--------|
| JavaScript/TypeScript | Jest / Vitest | jest.mock / vitest.mock | expect |
| Python | pytest | pytest-mock / unittest.mock | assert |
| Java | JUnit 5 | Mockito | assertj |
| Go | testing | testify/mock | testing |

### 测试组织

#### 目录结构

```
src/
├── modules/
│   └── order/
│       ├── order.service.ts      # 生产代码
│       └── order.service.test.ts  # 单元测试
```

#### 命名规范

```javascript
// Jest 命名规范
describe('OrderService', () => {
  describe('calculateTotal', () => {
    it('应正确计算多个商品的总价', () => { ... });
    it('应处理空商品列表并返回0', () => { ... });
    it('应在数量为0时返回0', () => { ... });
    it('应正确处理小数金额', () => { ... });
  });

  describe('createOrder', () => {
    it('应在库存不足时抛出库存不足异常', () => { ... });
    it('应正确创建订单并扣减库存', () => { ... });
  });
});
```

### 测试示例

```javascript
// calculateTotal.test.js
describe('calculateTotal', () => {
  it('正确计算商品总价', () => {
    const items = [
      { price: 100, quantity: 2 },
      { price: 50, quantity: 1 }
    ];
    expect(calculateTotal(items)).toBe(250);
  });

  it('处理空数组', () => {
    expect(calculateTotal([])).toBe(0);
  });

  it('处理边界情况', () => {
    expect(calculateTotal([{ price: 0.01, quantity: 1 }])).toBeCloseTo(0.01);
  });

  it('处理负数价格应抛出错误', () => {
    expect(() => {
      calculateTotal([{ price: -10, quantity: 1 }]);
    }).toThrow('价格不能为负数');
  });
});
```

## 集成测试

### 测试目标

集成测试验证多个组件协同工作时的行为，确保模块间的交互符合预期。集成测试通常涉及：

- API端点与业务逻辑的集成
- 数据库读写操作
- 缓存读写一致性
- 消息队列的消息传递
- 第三方服务的集成（使用Mock或Testcontainers）

### 集成测试要求

#### 必须测试的场景

1. **数据持久化**: 创建、读取、更新、删除操作
2. **业务事务**: 多步骤操作的原子性和一致性
3. **级联操作**: 主从表、关联实体的联动
4. **API契约**: 请求格式、响应格式、状态码
5. **错误传播**: 下游服务错误是否正确向上传递

#### 集成测试分层

| 类型 | 描述 | 依赖 | 速度 |
|------|------|------|------|
| 组件测试 | 单个模块的完整测试，包含真实数据库 | Testcontainers | 中 |
| API测试 | HTTP层端到端测试 | Mock数据库 | 快 |
| 契约测试 | 微服务间接口契约验证 | Mock服务 | 快 |
| 消息测试 | 消息队列的生产消费 | RabbitMQ/Kafka | 慢 |

### 测试框架

| 类型 | 工具 | 适用场景 |
|------|------|----------|
| API测试 | Supertest, RestAssured | HTTP API |
| 数据库测试 | TestContainers, Dockertest | MySQL, PostgreSQL, MongoDB |
| 消息队列测试 |otestcontainers (Kafka/RabbitMQ) | 消息传递 |
| 契约测试 | Pact, Hoverfly | 微服务接口 |

### 测试示例

```javascript
// users.api.test.js
describe('POST /api/v1/users', () => {
  let app;
  let db;

  beforeAll(async () => {
    db = await new TestContainers.PostgreSQL();
    app = createApp({ database: db });
  });

  afterAll(async () => {
    await db.stop();
  });

  beforeEach(async () => {
    await db.query('TRUNCATE TABLE users RESTART IDENTITY');
  });

  it('创建用户成功', async () => {
    const res = await request(app)
      .post('/api/v1/users')
      .send({
        username: 'testuser',
        email: 'test@example.com',
        password: 'password123'
      })
      .expect(201);

    expect(res.body.code).toBe(0);
    expect(res.body.data.username).toBe('testuser');
    expect(res.body.data.email).toBe('test@example.com');
    expect(res.body.data.password).toBeUndefined(); // 密码不应返回
  });

  it('用户名重复返回409冲突', async () => {
    await db.query(
      'INSERT INTO users (username, email, password) VALUES ($1, $2, $3)',
      ['testuser', 'test2@example.com', 'hash')
    );

    const res = await request(app)
      .post('/api/v1/users')
      .send({
        username: 'testuser',
        email: 'test@example.com',
        password: 'password123'
      })
      .expect(409);

    expect(res.body.code).toBe(40901);
    expect(res.body.message).toContain('用户名已存在');
  });

  it('无效邮箱格式返回400', async () => {
    const res = await request(app)
      .post('/api/v1/users')
      .send({
        username: 'testuser',
        email: 'invalid-email',
        password: 'password123'
      })
      .expect(400);

    expect(res.body.code).toBe(40001);
    expect(res.body.errors).toContainEqual({
      field: 'email',
      message: '邮箱格式不正确'
    });
  });
});
```

## E2E 测试

### 测试目标

端到端测试模拟真实用户场景，从用户界面或API入口开始，验证整个系统的行为。E2E测试位于测试金字塔顶端，应聚焦于最关键的 用户路径。

### E2E测试要求

#### 必须覆盖的关键路径

| 优先级 | 用户路径 | 测试目的 | 频率 |
|--------|----------|----------|------|
| P0 | 用户注册 → 登录 → 登出 | 认证流程完整性 | 每次构建 |
| P0 | 核心业务主流程 | 核心功能可用性 | 每次构建 |
| P0 | 支付/下单流程 | 资金安全 | 每次构建 |
| P1 | 密码重置 | 账户恢复能力 | 每日 |
| P1 | 搜索 → 浏览 → 下单 | 转化漏斗 | 每日 |
| P2 | 社交分享功能 | 扩展功能 | 每周 |
| P2 | 通知提醒 | 辅助功能 | 每周 |

#### E2E测试策略

1. **关键路径优先**: P0用例必须100%通过，P1达到90%，P2达到70%
2. **环境隔离**: 每个测试套件使用独立的测试数据
3. **幂等性**: 测试可重复运行，不互相影响
4. **失败隔离**: 单个测试失败不应级联影响其他测试
5. **截图/录像**: 失败时自动记录，便于排查

### 测试框架

| 框架 | 语言 | 特点 | 适用场景 |
|------|------|------|----------|
| Playwright | TypeScript/JavaScript | 跨浏览器、支持移动端 | 推荐首选 |
| Cypress | JavaScript | 易于上手、实时reload | 简单Web应用 |
| Selenium | 多语言 | 生态成熟、支持老浏览器 | 遗留系统 |

### 测试示例

```typescript
// user-flow.spec.ts (Playwright)
import { test, expect } from '@playwright/test';

test.describe('用户注册流程', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/');
    // 清理可能存在的测试数据
  });

  test('新用户注册成功并自动登录', async ({ page }) => {
    await page.click('text=注册');

    await page.fill('[name="username"]', `testuser_${Date.now()}`);
    await page.fill('[name="email"]', `test_${Date.now()}@example.com`);
    await page.fill('[name="password"]', 'Password123!');
    await page.fill('[name="confirmPassword"]', 'Password123!');
    await page.click('[type="submit"]');

    // 验证跳转到首页
    await expect(page).toHaveURL('/dashboard');
    await expect(page.locator('.user-name')).toBeVisible();
  });

  test('注册时密码强度不足应显示错误', async ({ page }) => {
    await page.click('text=注册');

    await page.fill('[name="username"]', 'testuser');
    await page.fill('[name="email"]', 'test@example.com');
    await page.fill('[name="password"]', '123');
    await page.click('[type="submit"]');

    await expect(page.locator('.password-error')).toContainText(
      '密码长度至少8位，需包含数字和字母'
    );
  });
});

test.describe('用户登录流程', () => {
  test('使用正确凭据登录成功', async ({ page }) => {
    // 先创建测试用户
    const testUser = await createTestUser();

    await page.goto('/login');
    await page.fill('[name="username"]', testUser.username);
    await page.fill('[name="password"]', testUser.password);
    await page.click('[type="submit"]');

    await expect(page).toHaveURL('/dashboard');
    await expect(page.locator('.user-name')).toContainText(testUser.username);
  });

  test('错误密码应显示错误提示', async ({ page }) => {
    const testUser = await createTestUser();

    await page.goto('/login');
    await page.fill('[name="username"]', testUser.username);
    await page.fill('[name="password"]', 'wrongpassword');
    await page.click('[type="submit"]');

    await expect(page.locator('.error-message')).toContainText('用户名或密码错误');
    await expect(page).toHaveURL('/login');
  });
});
```

## 覆盖率要求

### 覆盖率指标定义

| 指标 | 定义 | 意义 |
|------|------|------|
| 行覆盖率 | 已执行的代码行数 / 总代码行数 | 代码被执行的比例 |
| 分支覆盖率 | 已执行的分支数 / 总分支数 | 条件分支的覆盖程度 |
| 函数覆盖率 | 已执行的函数数 / 总函数数 | 函数被调用的比例 |
| 语句覆盖率 | 已执行的语句数 / 总语句数 | 与行覆盖率类似，统计粒度更细 |

### 覆盖率目标

#### 整体目标

| 项目阶段 | 行覆盖率 | 分支覆盖率 | 说明 |
|----------|----------|------------|------|
| 新项目 | ≥80% | ≥70% | 起步标准 |
| 成熟项目 | ≥85% | ≥75% | 持续提升 |
| 核心模块 | ≥90% | ≥80% | 重点保障 |

#### 差异化管理

| 模块类型 | 最低行覆盖率 | 最低分支覆盖率 |
|----------|-------------|----------------|
| 核心业务逻辑 | 85% | 75% |
| 公共工具库 | 95% | 85% |
| 数据访问层 | 80% | 70% |
| API控制器 | 90% | 80% |
| 中间件 | 85% | 75% |
| 配置管理 | 70% | 60% |

### 覆盖率报告

#### 生成报告

```bash
# Jest + TypeScript
npm run test:unit -- --coverage --coverageReporters=text --coverageReporters=lcov

# Vitest
npx vitest run --coverage --coverage.provider=v8

# pytest
pytest --cov=src --cov-report=html --cov-report=term-missing
```

#### 覆盖率门禁

```yaml
# .github/workflows/test.yml
- name: Check Coverage
  run: |
    npx jest --coverage --coverageThreshold='{
      "global": {
        "lines": 80,
        "branches": 70,
        "functions": 80,
        "statements": 80
      }
    }'
```

### 覆盖率注意事项

1. **覆盖率是手段不是目的**: 100%覆盖率不等于高质量测试
2. **关注未覆盖的代码**: 分析为什么某些代码没有被覆盖
3. **高风险区域优先**: 将覆盖率资源向核心业务和频繁变更区域倾斜
4. **渐进式提升**: 在重构或新项目中逐步提升覆盖率要求

```javascript
const userFactory = {

    email: faker.internet.email(),

      ...user,
      password: hashedPassword
    });

  createBatch: async (count, overrides = {}) => {
    return Promise.all(
      Array.from({ length: count }, () => userFactory.create(overrides))
    );
  }
};
```

## CI 集成

### 测试执行流程

```yaml
# .github/workflows/test.yml
name: Test Pipeline

on: [push, pull_request]

jobs:
  unit-tests:
    name: Unit Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4

          node-version: '20'
      - run: npm ci
      - run: npm run test:unit -- --coverage
      - uses: codecov/codecov-action@v3

          files: ./coverage/lcov.info

  integration-tests:
    name: Integration Tests
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:15

          POSTGRES_PASSWORD: test
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
    steps:
      - uses: actions/checkout@v4
      - run: npm run test:integration
      - run: npm run test:contract

      - uses: actions/checkout@v4
      - run: npx playwright install --with-deps

        with:
          name: playwright-report
          path: playwright-report/
```

## 性能测试

### 性能测试类型

| 类型 | 目的 | 指标 | 持续时间 |
|------|------|------|----------|
| 负载测试 | 验证正常负载下的性能 | 响应时间、QPS | 5-30分钟 |
| 压力测试 | 找出系统瓶颈 | 崩溃点、最大QPS | 10-60分钟 |
| 浸泡测试 | 发现内存泄漏等问题 | 长期稳定性 | 数小时到数天 |
| 尖峰测试 | 验证突发流量处理 | 弹性恢复能力 | 10-30分钟 |

### 性能指标要求

### k6配置示例

```javascript
// load-test.js
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate, Trend } from 'k6/metrics';

const errorRate = new Rate('errors');

const apiLatency = new Trend('api_latency');

export const options = {
  stages: [
    { duration: '2m', target: 100 },   // 预热
    { duration: '5m', target: 500 },   // 正常负载
    { duration: '2m', target: 1000 },  // 峰值
    { duration: '5m', target: 1000 },  // 持续峰值
    { duration: '2m', target: 0 },    // 冷却
  ],
  thresholds: {
    http_req_duration: ['p(95)<1000'],
    http_req_failed: ['rate<0.01'],
    errors: ['rate<0.1'],
  },
};

export default () => {
  const res = http.get('https://api.example.com/v1/products');

  apiLatency.add(res.timings.duration);

  const success = check(res, {
    'status is 200': (r) => r.status === 200,
    'response has data': (r) => r.json('data') !== undefined,
  });

  errorRate.add(!success);

  sleep(1);
};
```
