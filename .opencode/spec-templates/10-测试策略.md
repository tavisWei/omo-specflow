## 2. 测试金字塔（Test Pyramid）

<!-- AGENT: 先按项目类型确定比例，再决定工具和执行频率。不要写固定 70/20/10 后不解释。 -->

### 2.1 项目类型驱动的金字塔（Project-Type-Specific Pyramid）

| 项目类型 Project Type | 单元 Unit | 集成 Integration | 契约 Contract | E2E / Smoke | 说明 Guidance |
|---|---:|---:|---:|---:|---|
| Web 全栈 Web Fullstack | 50-60% | 20-25% | 10-15% | 10-15% | 页面与后端双边验证，关键路径需 E2E |
| API 服务 API Service | 45-55% | 25-35% | 10-20% | 5-10% | 以接口、数据、一致性为主，E2E 以 smoke/API journey 为主 |
| CLI 工具 CLI Tool | 60-75% | 15-25% | 0-10% | 5-10% | 侧重命令行为、文件输入输出、参数边界 |
| 数据密集/工作流系统 Workflow / Data-heavy | 40-50% | 25-35% | 10-15% | 10-15% | 重点放在状态流转、迁移、并发和回归 |

### 2.2 分层裁定规则（Layer Selection Rules）

1. **业务逻辑可纯函数化** → 优先单元测试。
2. **涉及数据库、缓存、消息、文件系统、外部服务适配** → 集成测试。
3. **跨服务/跨模块接口稳定性很重要** → 契约测试。
4. **关键用户路径、核心页面跳转、支付/登录/提交流程** → E2E/Smoke。
5. **迁移、索引、种子、权限、越权、并发写入** → 不可仅靠单元测试，至少需要集成测试。

### 2.3 金字塔执行频率（Execution Frequency Matrix）

| 层级 Layer | 本地 Local | PR / Merge Request | 主干 Main | 发布前 Pre-release |
|---|---|---|---|---|
| Unit | 高频 / 保存后可跑 | 必跑 | 必跑 | 必跑 |
| Integration | 按模块变更跑 | 必跑（受影响模块） | 必跑 | 必跑 |
| Contract | 按接口变更跑 | 必跑（核心接口） | 必跑 | 必跑 |
| E2E / Smoke | 可选抽样 | P0 必跑 | P0 + P1 必跑 | 全量关键路径必跑 |
| Performance | 本地可选 | 条件触发 | 定时或主干触发 | 发布前基线对比 |
| Security | 本地可选 | 依赖/SAST 必跑 | 必跑 | DAST/人工复核 |
| Migration / Seed | 变更 DB 时必跑 | 变更 DB 时必跑 | 变更 DB 时必跑 | 生产前 rehearsal |

### 2.4 测试层与证据映射（Layer → Evidence Mapping）

| 层级 Layer | 最低证据 Minimum Evidence |
|---|---|
| Unit | 测试日志 + 覆盖率摘要 + 失败列表 |
| Integration | 测试日志 + 环境依赖版本 + 关键断言结果 |
| Contract | 契约 diff / schema 验证结果 + 响应示例 |
| E2E | 通过/失败列表 + trace/screenshot/video（失败必备） |
| Performance | 指标表 + 基线对比 + 结论 |
| Security | 扫描报告 + 风险分级 + 处置结果 |
| Migration | 空库迁移结果 + 升级结果 + 回滚/恢复说明 |

- 用户故事测试：`T-US-001-01`

### 3.4 映射生成规则（Mapping Rules）

1. 每个 P0 故事至少包含 1 条成功路径和 1 条失败路径。
2. 每个写接口至少包含：正常写入、校验失败、权限失败、并发/冲突失败。
3. 每个页面主路径至少包含：进入、加载、提交/跳转、异常恢复。
4. 每个数据库高风险约束至少对应 1 条集成测试：唯一键、外键、状态机、迁移、seed、一致性。
5. 测试 ID 必须出现在测试代码注释、报告或任务清单中，保证可追踪。

## 4. 单元测试（Unit Tests）

<!-- AGENT: 单元测试负责“快、稳、细”地验证业务规则与边界，不替代集成/E2E。 -->

### 4.1 单元测试目标（Unit Test Goal）

- 验证纯业务规则、校验逻辑、状态机、格式转换、权限判断、错误映射。
- 尽可能在不依赖真实数据库/网络的情况下快速定位回归。
- 为重构提供秒级反馈。

### 4.2 必测对象（Must-Test Targets）

| 对象 Target | 是否必测 | 说明 |
|---|---|---|
| 领域服务 / service / use-case | yes | 核心业务规则 |
| 校验器 validators / schemas | yes | 输入合法性和边界 |
| 权限判断 / guards / policy | yes | 越权风险 |
| 状态流转函数 | yes | allow / reject 规则 |
| DTO / mapper / formatter | yes | 字段转换与脱敏 |
| 简单 getter / framework glue code | no / 条件 | 仅当包含业务逻辑时测试 |

### 4.3 覆盖率要求（Unit Coverage Contract）

| 模块类型 Module Type | 行覆盖率 Lines | 分支覆盖率 Branches | 函数覆盖率 Functions |
|---|---:|---:|---:|
| 核心业务逻辑 Core Domain | ≥85% | ≥75% | 100% |
| 权限/认证 Auth / Policy | ≥90% | ≥80% | 100% |
| 校验/转换 Validators / Mappers | ≥90% | ≥85% | 100% |
| 数据访问适配层 Repository adapters | ≥70% | ≥60% | ≥90% |
| 遗留/过渡区域 Legacy / Transitional | ≥60% | ≥50% | 协商但需解释 |

### 4.4 单元测试硬规则（Unit Hard Rules）

1. 外部依赖（数据库、网络、文件系统、时间、随机数）必须可控：mock、stub 或 fake。
2. 每个核心函数至少覆盖：正常路径、边界条件、异常路径、分支条件。
3. 安全或财务相关逻辑必须覆盖负面样例，不能只测 happy path。
4. 若使用 snapshot，必须只用于稳定 UI/序列化片段，不得替代语义断言。
5. 单元测试失败必须能指向具体规则，不允许“should work”式命名。

## 5. 集成测试（Integration Tests）

<!-- AGENT: 集成测试负责验证模块边界和真实依赖协作，特别是 API + DB + 缓存/消息/文件系统。 -->

### 5.1 集成测试目标（Integration Test Goal）

- 验证真实数据持久化、事务、一致性、错误传播、授权边界。
- 保证应用层、数据层和外部适配层协同工作时符合 API/数据库契约。

### 5.2 必测场景（Must-Test Scenarios）

1. CRUD：创建、读取、更新、删除（若有软删除则验证可见性与恢复语义）。
2. 事务：多步骤写入的原子性与回滚。
3. 约束：唯一键、外键、非空、状态流转、乐观锁。
4. API 契约：请求/响应结构、状态码、错误码、脱敏字段。
5. 权限边界：不同角色、不同资源归属、未认证/已认证/越权。

### 5.3 集成测试环境契约（Environment Contract）

| 组件 Component | 要求 Requirement |
|---|---|
| 数据库 Database | 使用临时数据库 / Testcontainers / 独立 schema，不得污染共享环境 |
| 种子数据 Seed | 使用 07-数据库设计 中定义的最小种子集或测试工厂 |
| 缓存 / 队列 Cache / MQ | 可使用容器化依赖或协议级 fake，但必须说明 |
| 时钟 Clock | 可冻结或可注入，以便断言时间相关行为 |
| 外部服务 External APIs | 使用 stub/mock server 或 sandbox |

### 5.4 API 集成测试示例（Worked Example）

```typescript
describe('POST /api/v1/resources', () => {
  beforeEach(async () => {
    await truncateTables(['resource_status_history', 'resources', 'users']);
    await seedBaseUsers();
  });

  it('T-API-RESOURCE-CREATE-01 创建资源成功', async () => {
    const token = await loginAs('user@example.com');

    const res = await request(app)
      .post('/api/v1/resources')
      .set('Authorization', `Bearer ${token}`)
      .send({ title: 'New Resource', status: 'draft' })
      .expect(201);

    expect(res.body.code).toBe(0);
    expect(res.body.data.title).toBe('New Resource');
    expect(await db.resource.count()).toBe(1);
  });

  it('T-API-RESOURCE-CREATE-02 标题缺失返回 400/422', async () => {
    const token = await loginAs('user@example.com');

    const res = await request(app)
      .post('/api/v1/resources')
      .set('Authorization', `Bearer ${token}`)
      .send({ title: '' })
      .expect(422);

    expect(res.body.code).not.toBe(0);
    expect(res.body.errors?.[0]?.field).toBe('title');
  });
});
```

### 5.5 数据一致性测试（Data Integrity Test Contract）

| 风险 Risk | 最低测试要求 Minimum Test |
|---|---|
| 唯一键 Unique Key | 同一业务键重复创建时必须失败 |
| 外键 Foreign Key | 引用不存在对象时必须失败或被应用层拦截 |
| 乐观锁 Versioning | 旧版本更新必须返回冲突 |
| 状态机 State Machine | 非法状态跳转必须拒绝并不写历史 |
| 软删除 Soft Delete | 被软删数据默认不可见，按规则可恢复/不可恢复 |

### 5.6 数据库迁移 / Seed 集成测试（DB Integration Contract）

1. **空库迁移测试**：从空数据库执行所有 migration，必须成功。
2. **增量迁移测试**：从上一稳定版本升级到当前版本，必须成功。
3. **seed 测试**：执行 seed 后必须满足最小数据集约束。
4. **约束测试**：seed 及后续写入不得违反唯一键、外键、枚举和默认值规则。
5. **兼容性测试**：若存在 backfill 或两阶段迁移，必须验证旧数据仍可读，新数据可写。

## 6. 契约测试（Contract Tests）

<!-- AGENT: 当 API Schema、事件 Schema、消息协议或跨模块 DTO 是团队协作界面时，契约测试为强制层。 -->

### 6.1 契约测试目标（Contract Test Goal）

- 防止接口字段漂移、响应结构破坏、错误码失真、枚举不一致。
- 保证下游页面、客户端、CLI 或外部集成在升级时不被静默破坏。

### 6.2 契约来源（Contract Sources）

| 来源 Source | 必须验证内容 |
|---|---|
| `03-接口文档` | 路径、方法、状态码、字段、错误码、分页结构 |
| `07-数据库设计` | 枚举、命名映射、敏感字段不可暴露 |
| 前端页面规格 `05/06` | 页面使用的字段和筛选参数真实存在 |
| 外部协议（Webhook / MQ） | 事件名、payload 字段、版本号 |

### 6.3 必测契约（Mandatory Contracts）

1. 核心 P0 接口的成功响应体。
2. 核心 P0 接口的失败响应体（400/401/403/404/409/422/500 中相关项）。
3. 分页、排序、筛选字段契约。
4. 枚举值与错误码契约。
5. 脱敏字段契约：如 `passwordHash`、token、内部审计字段不得泄露。

### 6.4 契约差异处理（Contract Diff Handling）

| 变更类型 Change Type | 处理规则 |
|---|---|
| 增加可选字段 | 可接受，但需更新文档和消费者测试 |
| 删除字段 / 改名 | 破坏性变更，必须阻断，除非已版本化 |
| 枚举减少或语义变化 | 阻断，必须同步迁移和消费者 |
| 错误码变更 | 阻断，需更新调用侧和测试 |
| 字段从非空变可空 / 反之 | 高风险，需要审查和兼容策略 |

### 6.5 契约测试示例（Example）

```typescript
it('T-API-LOGIN-01 登录响应遵守契约', async () => {
  const res = await request(app)
    .post('/api/v1/auth/login')
    .send({ email: 'user@example.com', password: 'User123!' })
    .expect(200);

  expect(res.body).toMatchObject({
    code: 0,
    message: expect.any(String),
    data: {
      user: {
        id: expect.any(String),
        email: 'user@example.com',
      },
    },
  });

  expect(JSON.stringify(res.body)).not.toContain('passwordHash');
  expect(JSON.stringify(res.body)).not.toContain('refreshToken');
});
```

## 7. E2E / Smoke 测试（End-to-End / Smoke Tests）

<!-- AGENT: E2E 不求多，而求关键路径、可证据化、可阻断发布。 -->

### 7.1 E2E 目标（E2E Goal）

- 模拟真实用户路径，验证页面、接口、权限、状态流转和持久化协同工作。
- 在发布前给出“关键业务是否仍可走通”的高置信度结论。

### 7.2 关键路径矩阵（Critical Journey Matrix）

| 优先级 | 路径 Journey | 适用项目 | 频率 | 通过要求 |
|---|---|---|---|---|
| P0 | 登录 → 进入工作台 / 主列表 | web, api-admin | 每次 PR / 每次发布 | 100% |
| P0 | 列表 → 详情 → 编辑 → 保存 | web | 每次 PR / 每次发布 | 100% |
| P0 | 关键写操作（下单/支付/审批/发布） | 视业务 | 每次发布 | 100% |
| P1 | 设置修改并生效 | web | 每日 / 主干 | ≥95% |
| P1 | 搜索 / 筛选 / 分页 | web, api | 每日 / 主干 | ≥95% |
| P2 | 辅助功能 / 长尾路径 | 视业务 | 定时 | ≥80% |

### 7.3 E2E 环境规则（Environment Rules）

1. 测试环境数据必须隔离，避免与共享环境混淆。
2. 每个测试必须可重复执行，不依赖上一条测试留下的数据。
3. 失败时必须自动采集至少一种证据：screenshot、trace、video、HAR、console log。
4. 涉及第三方支付/登录的场景必须使用 sandbox 或受控 stub，不得打真实生产流量。
5. 对于 API-only 项目，可将 smoke test 定义为“关键接口旅程测试”替代 UI E2E。

### 7.4 Playwright 示例（Worked Example）

```typescript
import { test, expect } from '@playwright/test';

test('T-E2E-RESOURCE-EDIT-01 用户编辑资源并看到保存结果', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('邮箱').fill('user@example.com');
  await page.getByLabel('密码').fill('User123!');
  await page.getByRole('button', { name: '登录' }).click();

  await expect(page).toHaveURL(/dashboard|resources/);

  await page.goto('/resources');
  await page.getByText('Draft Resource').click();
  await page.getByRole('button', { name: '编辑' }).click();

  await page.getByLabel('标题').fill('Draft Resource Updated');
  await page.getByRole('button', { name: '保存' }).click();

  await expect(page.getByText('保存成功')).toBeVisible();
  await expect(page.getByText('Draft Resource Updated')).toBeVisible();
});
```

### 7.5 页面异常恢复验证（Recovery Cases）

| 场景 Scenario | 最低验证 Minimum Verification |
|---|---|
| 登录失败 | 错误提示可见，输入不丢失 |
| 网络失败 | 显示重试或保留当前输入 |
| 403 / 权限不足 | 显示只读或跳转 403，行为一致 |
| 404 / 数据不存在 | 显示空/错误页，可返回列表 |
| 422 / 校验失败 | 字段级错误可见，表单值保留 |

## 8. 覆盖率与风险覆盖（Coverage & Risk Coverage）

<!-- AGENT: 覆盖率不是目标本身，而是最低信号。必须和风险覆盖一起使用。 -->

### 8.1 覆盖率指标（Coverage Metrics）

| 指标 Metric | 定义 | 说明 |
|---|---|---|
| 行覆盖率 Lines | 被执行代码行 / 总代码行 | 基础指标 |
| 分支覆盖率 Branches | 被执行分支 / 总分支 | 条件复杂度的重要指标 |
| 函数覆盖率 Functions | 被调用函数 / 总函数 | 功能入口覆盖 |
| 风险覆盖率 Risk Coverage | 已验证高风险点 / 高风险点总数 | 本模板新增的核心指标 |

### 8.2 风险覆盖最小要求（Minimum Risk Coverage）

| 风险类型 Risk Type | 最低要求 |
|---|---|
| 认证 / 权限 | 成功 + 失败 + 越权路径都必须覆盖 |
| 数据写入 | 成功 + 校验失败 + 冲突失败 + 回滚行为 |
| 数据查询 | 正常 + 空数据 + 不存在 + 权限边界 |
| 页面流程 | 主路径 + 至少 1 条失败恢复路径 |
| 迁移 / seed | 空库、增量库、重复执行 seed |
| 安全 | 依赖扫描 + 至少 1 套鉴权/输入攻击验证 |

### 8.3 覆盖率门禁（Coverage Gates）

| 级别 Level | 行覆盖率 | 分支覆盖率 | 额外条件 |
|---|---:|---:|---|
| 全局 Global | ≥80% | ≥70% | P0 风险覆盖率 100% |
| 核心模块 Critical Modules | ≥85% | ≥75% | 关键函数 100% 有断言 |
| 认证/权限 Auth/Policy | ≥90% | ≥80% | 负面路径必须存在 |

### 8.4 覆盖率使用规则（Coverage Usage Rules）

1. 不允许用无断言测试、机械 snapshot 或覆盖无意义代码来“刷覆盖率”。
2. 覆盖率未达标时，必须指出未覆盖的高风险区是否仍然存在。
3. 覆盖率达标但关键路径未验证，仍视为不通过。
4. 风险覆盖率优先级高于全局行覆盖率。

## 9. 测试数据管理（Test Data Management）

<!-- AGENT: 测试数据必须和 07-数据库设计 中 seed / schema / 枚举 / migration 契约保持一致。 -->

### 9.1 数据层级（Data Layers）

| 层级 Layer | 用途 | 数据来源 | 是否可复用 |
|---|---|---|---|
| Mock Data | 单元测试 | inline factory / fixture | 高 |
| Fixture Data | 集成测试 | yaml/json/sql/seed modules | 中 |
| Factory Data | 集成 / E2E | 代码工厂动态创建 | 高 |
| Baseline Seed | 本地 / CI / Demo | 07 中定义 seed | 高 |
| Masked Snapshot | 预发布 / 回归 | 脱敏生产副本 | 低，需谨慎 |

### 9.2 数据规则（Data Rules）

1. 测试数据必须使用假数据，不得使用真实用户隐私。
2. 所有 fixture/factory 字段必须符合数据库约束和 API 契约。
3. 需要验证权限/归属时，必须至少准备 2 个不同角色/不同所有者的数据集。
4. 需要验证状态流转时，必须准备多个状态的实体。
5. 需要验证并发时，必须能创建相同目标的双写场景。

### 9.3 数据工厂示例（Factory Example）

```typescript
export const resourceFactory = {
  build: (overrides = {}) => ({
    title: `Resource_${Date.now()}`,
    description: 'test resource',
    status: 'draft',
    ...overrides,
  }),

  create: async (overrides = {}) => {
    const input = resourceFactory.build(overrides);
    return db.resource.create({ data: input });
  },
};
```

### 9.4 数据清理规则（Cleanup Rules）

- 单元测试：每个 case 清理 mock 状态和 fake timers。
- 集成测试：每个 suite 或 case 使用事务回滚 / truncate / isolated schema。
- E2E：优先独立账号和独立资源 ID，结束后清理或让环境定时回收。
- Migration rehearsal：使用一次性数据库实例，执行完即销毁。

## 10. Flaky Test 管理（Flaky Test Handling）

<!-- AGENT: Flaky test 不是“偶尔失败就重跑”的借口，而是需要分级处置的质量问题。 -->

### 10.1 Flaky 定义（Definition）

若测试在**代码未变化**的条件下出现非确定性失败，即视为 flaky。常见来源：时间依赖、共享状态、并发竞争、网络不稳定、等待条件错误、脆弱选择器。

### 10.2 Flaky 分级（Severity Levels）

| 级别 | 定义 | 处置 |
|---|---|---|
| S1 | 阻断主干或发布的关键路径 flaky | 立即修复，必要时临时隔离并补强替代验证 |
| S2 | 高频 PR 失败但非发布关键路径 | 48 小时内修复 |
| S3 | 偶发、低优先路径 | 进入修复 backlog，但需标记原因 |

### 10.3 处置规则（Handling Rules）

1. 发现 flaky 后必须记录：测试 ID、失败频次、最近变更、怀疑原因、影响范围。
2. 允许有限重跑用于确认是否 flaky，但**不得**把无限重跑当成通过策略。
3. 被 quarantine 的测试必须：
   - 有 issue / task 跟踪
   - 有替代验证
   - 不属于 P0 发布关键路径
4. 关键路径测试若 flaky，不允许直接降级为非阻断，除非有等效更强验证替代。
5. 修复 flaky 后必须补充根因防护，如等待条件、数据隔离、时钟控制、稳定选择器。

### 10.4 Flaky 记录模板（Flaky Record Template）

| 字段 | 内容 |
|---|---|
| Test ID | `T-E2E-RESOURCE-EDIT-01` |
| Frequency | 3/20 runs |
| Suspected Cause | 页面跳转等待条件不稳定 |
| Severity | S1 / S2 / S3 |
| Temporary Mitigation | 使用稳定 locator + network idle / URL assert |
| Owner | <!-- AGENT: 负责人 --> |
| Due Date | <!-- AGENT: 截止日期 --> |

## 11. 性能测试（Performance Tests）

<!-- AGENT: 只对存在性能要求的项目启用；不要为了凑完整度而泛写。 -->

### 11.1 何时必做（When Performance Tests Are Required）

- `01-需求文档` 中出现明确性能 SLA/SLO。
- 列表/搜索/写操作吞吐量是核心竞争力。
- 发布包含数据库索引、查询、缓存、队列等高风险变更。

### 11.2 类型与指标（Types & Metrics）

| 类型 Type | 目的 Goal | 关键指标 Key Metrics |
|---|---|---|
| 负载测试 Load | 验证目标负载下表现 | P50/P95/P99、QPS、错误率 |
| 压力测试 Stress | 找到瓶颈和退化点 | 最大吞吐、失败模式 |
| 尖峰测试 Spike | 验证突发流量恢复能力 | 自动恢复、队列积压 |
| 浸泡测试 Soak | 发现泄漏和长期退化 | 内存、连接数、稳定性 |

### 11.3 发布前基线规则（Baseline Rules）

1. 所有性能测试结果都必须与上一稳定基线比较。
2. 若 P95 退化超过阈值（例如 20%），必须人工审查或阻断发布。
3. 涉及 DB schema / index 变更时，必须至少对受影响查询做一次基线比较。

### 11.4 k6 示例（Worked Example）

```javascript
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  vus: 50,
  duration: '2m',
  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const res = http.get('https://api.example.com/api/v1/resources?page=1&pageSize=20');
  check(res, {
    'status 200': (r) => r.status === 200,
    'has data': (r) => JSON.parse(r.body).data !== undefined,
  });
}
```

## 12. 安全测试（Security Tests）

<!-- AGENT: 安全测试必须和系统攻击面相关，不要只列工具名。 -->

### 12.1 最小安全保障（Minimum Security Coverage）

| 风险 Risk | 最低验证 Minimum Verification |
|---|---|
| 认证绕过 | 未登录访问受保护资源返回 401 |
| 越权访问 | 非所有者/低权限角色访问受限资源返回 403 |
| 输入攻击 | SQL/NoSQL 注入、XSS、命令注入按项目类型验证 |
| 敏感信息泄露 | 响应、日志、错误堆栈不泄露秘密 |
| 依赖漏洞 | 依赖扫描无高危未处置漏洞 |
| 暴力破解 | 登录限流/锁定/监控策略存在 |

### 12.2 安全测试分层（Security Layers）

1. **SAST / 依赖扫描**：每次 PR 必跑。
2. **鉴权/权限自动化测试**：核心受保护接口和页面必跑。
3. **DAST / 渗透回归**：发布前或定期执行。
4. **人工复核**：涉及支付、密钥管理、管理后台、外部回调时强烈建议。

### 12.3 安全失败处理（Failure Handling）

- 高危漏洞：阻断合并/发布。
- 中危漏洞：需给出处置计划；若命中高风险面，升级为阻断。
- 低危漏洞：记录并进入 backlog，但不能在关键路径长期堆积。

### 14.1 推荐流水线（Recommended Pipeline）

```yaml
name: Test Pipeline

on: [push, pull_request]

jobs:

      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run db:migrate:test
      - run: npm run test:integration
      - run: npm run test:contract

  e2e-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4

          node-version: '20'
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npm run test:e2e
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
```

### 14.2 分支策略与触发条件（Branch / Trigger Rules）

| 触发 Trigger | 必跑项 Required Checks |
|---|---|
| PR 修改业务逻辑 | unit + integration |
| PR 修改 API 契约 | unit + integration + contract |
| PR 修改页面主流程 | unit + e2e smoke |
| PR 修改 DB schema / migration | unit + integration + migration rehearsal |
| 发布前 | 全量阻断项 + release gates |

### 14.3 CI 失败归类（CI Failure Classification）

- **编译/类型/lint 失败**：立即阻断。
- **阻断测试失败**：立即阻断。
- **非阻断测试失败**：允许通过需人工批准的场景必须在此事先定义。
- **基础设施故障**：可重试一次，但必须标记为 infra，而不是吞掉失败。

## 15. 发布门禁（Release Gates）

<!-- AGENT: 本节必须可被 Release Agent 直接执行。 -->

### 15.1 阻断级门禁（Blocking Release Gates）

| 门禁 Gate | 条件 Condition | 阻断规则 |
|---|---|---|
| P0 单元/集成/契约测试 | 全通过 | 任一失败阻断 |
| P0 E2E / Smoke | 100% 通过 | 任一失败阻断 |
| 覆盖率 Gate | 达到 8.3 约定 | 未达标阻断，除非有批准例外 |

| Security Gate | 无未处置高危 | 有高危即阻断 |
| Flaky Gate | 无 S1 flaky 未处置 | 有则阻断 |
| Story Traceability Gate | 所有 P0 故事均有证据 | 缺失阻断 |

### 15.2 条件放行门禁（Conditional Gates）

| 门禁 Gate | 可放行条件 |
|---|---|
| P1 E2E 失败 | 有明确非关键影响评估 + 产品/QA 审批 + 回归计划 |
| 分支覆盖率略低 | 全部高风险点已覆盖 + 有豁免记录 |
| 中危安全项 | 有时限修复计划 + 不命中关键攻击面 |
| 性能轻微退化 | 未超过业务阈值且已有性能债务记录 |

### 15.3 发布前 Smoke 清单（Pre-Release Smoke Checklist）

- [ ] 认证链路可用
- [ ] 至少一条核心读路径可用
- [ ] 至少一条核心写路径可用
- [ ] 权限拒绝路径可用
- [ ] 关键配置/设置链路可用（如适用）
- [ ] DB migration / seed / startup 无阻塞异常

## 16. 多 Agent 执行指南（Multi-Agent Execution Guide）

<!-- AGENT: 用于 OMO 流程直接分工。 -->

### 16.1 推荐分工（Suggested Agent Split）

| Agent 角色 | 主要输入 | 主要输出 | 必须回传 |
|---|---|---|---|
| Unit Test Agent | 01, 02, 业务代码 | 业务规则测试 | 覆盖率 + 失败列表 |
| Integration Agent | 03, 07, 应用/DB | API/DB/事务测试 | 约束验证结果 |
| E2E Agent | 05, 06, 03 | 用户路径脚本 | trace / screenshot / report |
| Security Agent | 01, 03, 02 | 鉴权/输入攻击/扫描结果 | 风险清单 |
| Performance Agent | 01 NFR, 02, 07 | 基线测试与对比 | 指标表 + 结论 |
| Release / QA Agent | 全部 | 汇总证据、做放行判断 | pass / fail 结论 |

### 16.2 执行顺序（Execution Order）

1. Requirements Agent 先输出故事、AC、NFR。
2. API / DB Agent 产出接口契约和数据库契约。
3. Unit / Integration Agent 并行生成底层验证。
4. 页面稳定后，E2E Agent 生成关键路径。
5. Security / Performance Agent 视项目风险并行补充。
6. QA / Release Agent 聚合证据并执行 15. 发布门禁。

### 16.3 交接契约（Handoff Contract）

- Unit Agent 必须输出覆盖率和风险点说明。
- Integration Agent 必须输出 API、DB、migration、seed 的通过结果。
- E2E Agent 必须输出关键路径报告与失败证据。
- QA Agent 必须输出 Story Traceability 和最终阻断结论。
