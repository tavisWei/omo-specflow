## 设计原则（Design Principles）
1. **一致性**: 整个应用保持视觉和交互的一致性
2. **层次性**: 通过大小、颜色、间距区分信息层次
3. **可访问性**: 满足 WCAG 2.1 AA 级标准
4. **响应式**: 适配桌面端、平板端、移动端

## 动效规范
- **过渡时长**: 200ms(快速), 300ms(正常), 500ms(缓慢)
- **缓动函数**: `cubic-bezier(0.4, 0, 0.2, 1)`
- **动画原则**: 
  - 避免过度使用动画
  - 动画应提供反馈，不打断用户流程
  - 入场动画优先于退场动画

## 编码规范

> 💡 **填写说明**: 根据项目技术栈补充具体的命名规则和格式化工具配置

### 命名规范

#### 通用原则
- **清晰性**: 名称应描述用途，无需猜测
- **简洁性**: 避免冗余前缀后缀
- **一致性**: 同一概念全程使用相同名称

#### 命名约定
| 类型 | 约定 | 示例 |
|------|------|------|
| 文件/类/模块 | 帕斯卡命名 | `UserProfile`, `OrderService` |
| 函数/方法 | 驼峰命名 | `getUserById`, `calculateTotal` |
| 常量 | 全大写下划线分隔 | `MAX_RETRY_COUNT`, `API_BASE_URL` |
| 变量 | 驼峰命名，名词形式 | `userName`, `totalAmount` |
| 布尔值 | is/has/can 前缀 | `isActive`, `hasPermission` |
| 私有成员 | 下划线前缀 | `_internalState` |

#### 命名黑名单
- 避免单字母命名（循环变量除外）
- 避免缩写（除非通用且无歧义）
- 避免拼音或中英混合

```
# 不推荐
getUserByID, usrNme, str, data, temp

# 推荐
getUserById, userName, firstName, fullName
```

### 代码格式化

#### 缩进与空白
- 使用 **空格** 而非 Tab，缩进宽度 2 或 4
- 行末不保留多余空白
- 方法之间空一行，逻辑块之间空一行

#### 长度限制
- 单行不超过 **120 字符**
- 函数不超过 **50 行**（超出则考虑拆分）
- 文件不超过 **500 行**（超出则考虑拆分）

#### 对齐
- 变量声明左对齐
- 链式调用可在 `.` 处换行
- 条件分支对齐关键字

> 📝 **提示**: 指定团队统一的格式化工具（如 Prettier、ESLint、Black），并在 CI 中强制执行

### 结构规范

#### 模块组织
```
模块/
├── core/           # 核心业务逻辑
├── features/       # 按功能划分模块
├── shared/         # 共享工具和组件
├── config/         # 配置
└── main.ts         # 入口文件
```

#### 依赖方向
- 高层模块不依赖低层模块
- 共享模块只被业务模块依赖
- 避免循环依赖

## Git 提交规范

> 💡 **填写说明**: 团队可根据需要选择 Conventional Commits 或其他约定

### 提交信息结构

```
<类型>(<范围>): <简短描述>

正文（可选）：说明为什么改、影响什么

页脚（可选）：关联 issue / breaking change / refs
```

### 提交类型

| 类型 | 说明 | 示例 |
|------|------|------|
| feat | 新功能 | `feat(user): add password reset` |
| fix | 修复缺陷 | `fix(checkout): resolve payment failure` |
| docs | 文档更新 | `docs: update README` |
| style | 格式调整（不影响功能） | `style: format code` |
| refactor | 重构（不改变功能） | `refactor(api): simplify validation` |
| perf | 性能优化 | `perf(list): improve render speed` |
| test | 添加或修改测试 | `test(auth): add login tests` |
| chore | 构建或辅助工具变动 | `chore: update dependencies` |
| revert | 回滚提交 | `revert: revert abc123` |

### 提交规则

#### 描述规范
- 使用动词开头：add, fix, update, remove, improve
- 首字母小写
- 不使用句号结尾
- 不超过 72 字符

```
# 不推荐
I fixed the bug with the login button
Fixed the issue
Update the code

# 推荐
fix(auth): handle expired session gracefully
feat(checkout): add coupon code support
```

#### 提交时机
- 每完成一个独立功能或修复提交一次
- 不要在提交中混合无关改动
- 提交前检查暂存区内容

#### 分支命名

| 类型 | 格式 | 示例 |
|------|------|------|
| 功能 | `feature/<描述>` | `feature/user-profile` |
| 修复 | `fix/<描述>` | `fix/login-redirect` |
| 发布 | `release/<版本>` | `release/v2.1.0` |
| 热修复 | `hotfix/<描述>` | `hotfix/payment-crash` |

> 📝 **提示**: 在 Git 钩子或 CI 中配置提交信息校验，确保格式统一

## 代码审查清单

> 💡 **填写说明**: 审查者检查时逐项确认，发现问题在评论中标注

### 功能性检查

- [ ] **需求对应**: 代码实现了需求文档中的所有功能点
- [ ] **边界处理**: 正确处理空值、空数组、极端值
- [ ] **错误处理**: 异常情况有合理处理，不会裸抛异常
- [ ] **用户体验**: 操作有适当反馈，loading 和错误状态友好

### 代码质量检查

- [ ] **可读性**: 变量和函数命名清晰，逻辑无需猜测
- [ ] **简洁性**: 无重复代码，无过度设计
- [ ] **函数单一职责**: 每个函数只做一件事
- [ ] **参数合理**: 参数数量不过多（建议不超过 3 个）

### 安全性检查

- [ ] **输入校验**: 用户输入经过验证
- [ ] **权限检查**: 敏感操作验证权限
- [ ] **无硬编码**: 无明文密码、密钥、API Key
- [ ] **SQL/命令注入**: 使用参数化查询或转义

### 性能检查

- [ ] **无阻塞主线程**: 耗时操作异步处理
- [ ] **无资源泄漏**: 连接、监听器、计时器正确关闭
- [ ] **懒加载**: 非首屏内容延迟加载
- [ ] **无重复请求**: 相同数据不重复拉取

### 可维护性检查

- [ ] **文档**: 复杂逻辑有注释说明
- [ ] **测试**: 核心逻辑有单元测试覆盖
- [ ] **配置化**: 硬编码值提取为配置
- [ ] **日志**: 关键操作有日志记录

### 审查意见标注

在评论中使用统一前缀：

| 前缀 | 含义 | 严重程度 |
|------|------|----------|
| `[must]` | 必须修改，否则无法合并 | 阻塞 |
| `[should]` | 建议修改，优化质量 | 中等 |
| `[nit]` | 小问题，风格偏好 | 轻微 |
| `[question]` | 需要澄清 | 讨论 |
| `[praise]` | 做得好的地方 | 鼓励 |

**示例**:
```
`[must]` 这个函数超过了 100 行，需要拆分
`[should]` 建议将 magic number 提取为常量
`[nit]` 变量命名可以更精确
`[question]` 这里的设计意图是什么？
```

## 注释规范

### 注释原则

1. **Why over What**: 解释为什么做，而非做了什么（代码本身应清晰表达做了什么）
2. **及时更新**: 代码变更时同步更新注释
3. **删除废弃**: 及时删除过时注释

### 注释类型

#### 文件头注释
```markdown
<!--
  模块名称: 用户认证
  功能描述: 处理用户注册、登录、令牌刷新
  依赖模块: token-service, validation-utils
  创建日期: 2024-01-15
-->
```

#### 函数注释
```markdown
/**
 * 获取用户详情
 * @param userId 用户 ID
 * @returns 用户信息，不存在返回 null
 *
 * @description
 * 从缓存优先读取，缓存命中则直接返回。
 * 缓存未命中时从数据库加载，并更新缓存。
 *
 * @example
 * const user = await getUserById('123');
 */
```

#### 行内注释
```javascript
// 使用 setTimeout 而非 setInterval，避免累积误差
// 参考: https://example.com/bug-tracker/123
const timer = setTimeout(calculate, 1000);
```

### 注释黑名单

```
# 不推荐
// loop through array          # 重复代码已知信息
// increment i                 # 无意义
// TODO: fix this later         # 模糊的待办
// This is a function          # 显而易见的描述

# 代替方案
// 每分钟采样一次，平衡精度和性能
// i++                          # 无需注释
// `[must]` 缓存过期逻辑有边界问题，需要修复
```

### 待办注释规范

```javascript
// `[must]` 性能: 未实现分页，大数据量会卡顿
// `[should]` 考虑支持离线模式
// `[question]` 是否需要支持多语言？
```

## 错误处理规范

### 错误处理原则

1. **早发现**: 在边界验证输入，及时暴露问题
2. **有分类**: 不同类型错误区分处理
3. **有意义**: 错误信息对用户和开发者都有价值
4. **不吞没**: 除非明确要忽略，否则必须处理或记录

### 错误分类

| 类型 | 说明 | 处理方式 |
|------|------|----------|
| 参数错误 | 调用方传入无效参数 | 校验后返回明确错误 |
| 业务错误 | 违反业务规则 | 返回业务错误码和提示 |
| 系统错误 | 外部服务、数据库等故障 | 降级或重试，记录日志 |
| 未知错误 | 预期外的异常 | 捕获、记录、返回通用错误 |

### 错误响应格式

```json
{
  "success": false,
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "用户不存在",
    "detail": "根据 ID u123 未找到对应用户"
  }
}
```

### 错误处理模式

#### 1. 参数校验
```
函数入口处校验所有参数
无效时立即返回错误，不继续执行
```

#### 2. Result 模式
```
不直接抛异常，而是返回 Result<T, E>
调用方显式处理成功和失败情况
```

#### 3. 降级处理
```
外部服务不可用时
返回缓存数据或默认值
记录降级日志
```

#### 4. 重试机制
```
对临时性故障（网络、超时）实施重试
限制重试次数和间隔
避免无限重试
```

### 日志规范

| 场景 | 级别 | 内容 |
|------|------|------|
| 正常流程 | Debug | 关键步骤 |
| 异常被捕获 | Warn | 业务异常信息 |
| 系统故障 | Error | 完整堆栈和上下文 |
| 安全相关 | Info | 登录、权限变更 |

```
# 日志内容应包含
时间戳 | 级别 | 请求 ID | 用户 ID | 操作 | 结果 | 耗时
```

### 异常处理黑名单

```javascript
// 不推荐
try { ... } catch (e) { }                    // 静默吞没
try { ... } catch (e) { throw e; }           // 重新抛出无价值
try { ... } catch (e) { console.log(e); }     // 仅打印未记录

// 推荐
try { ... } catch (e) { logger.error(e); return defaultValue; }
try { ... } catch (e) { throw new BusinessError(e.message); }
```

## 配置管理

> 💡 **填写说明**: 定义配置项的分类和管理方式

### 配置分类

| 类型 | 示例 | 管理方式 |
|------|------|----------|
| 环境变量 | API 地址、数据库连接 | 操作系统环境变量 |
| 应用配置 | 超时时间、重试次数 | 配置文件 |
| 功能开关 | 是否启用某功能 | 配置中心 |
| 业务规则 | 手续费比例、限额 | 数据库或配置 |

### 配置原则

- 环境相关配置通过环境变量注入
- 敏感配置（密钥、密码）不写入代码
- 配置项有默认值和校验规则
- 支持热更新而不必重启服务

## 性能规范

> 💡 **填写说明**: 定义性能基线和优化方向

### 性能指标

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| 首屏加载 | < 3s | Lighthouse |
| 接口响应 | < 500ms (P95) | APM 监控 |
| 交互响应 | < 100ms | 性能 API |

### 优化方向

- 减少请求数量和体积
- 利用缓存减少重复计算
- 懒加载非关键资源
- 避免不必要的重渲染和重计算
